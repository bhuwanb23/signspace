**Re-scoped, with what the repository actually had:** steps 1–3 are largely done already — the schema
exists (§2), six poses are authored (not two), and `SignSetLoader` + `HandPose.FromJson` read them through
`UnityWebRequest` because `File.ReadAllText` cannot read StreamingAssets on Android. What was genuinely
missing was step 4 (no timing anywhere) and the named artefact `PoseProvider.cs`.

**Two real bugs found by checking the code against the schema, both fixed:**

1. **`version` was never checked.** `POSE-FORMAT.md` §2 said "the loader refuses unknown versions". It
   did not — a version-2 file would have been read as if it were version 1, which is the entire point of
   having a version field. Now refused by `HandPose.SupportedVersion`, and `validate_poses.py` catches it
   at authoring time (proved: a version-2 file is reported as `schema version 2, this build reads 1`).
2. **Rotations were read POSITIONALLY.** A file whose `jointNames` were in a different order would have
   applied every rotation to the wrong joint — silently, while logging "26/26 loaded". Rotation i is now
   placed by **name** into canonical order, duplicates are rejected, and joints a file omits stay at
   identity instead of borrowing a neighbour's rotation. All six shipped files pass, verified.

## Why this exists
The product's content is data. Proving a stored pose reproduces faithfully and quickly is what separates a product from a demo.

## Do this
1. Define a minimal pose JSON: 26 joints, relative quaternions against a neutral capture, plus metadata fields.
2. Write a loader that applies the pose to the reference hand at runtime from `StreamingAssets`.
3. Hand-author two poses (any two, e.g. a fist and a spread hand) and confirm they reproduce visually.
4. Measure load time and pose-apply time on device — both should be negligible, but measure.
5. Draft `docs/02-tech/POSE-FORMAT.md` §1–3 from what actually worked.
