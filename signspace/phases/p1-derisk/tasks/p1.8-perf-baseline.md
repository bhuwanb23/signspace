# P1.8 — Measure the baseline frame budget on Quest 3S

**Phase:** P1 · **Est:** 45 min · **Depends on:** P1.1 · **Workstream:** W2
**Gate fed:** G1

## Why this exists
Forty percent of the remaining plan can be wrecked by a performance surprise on Day 8. Establish the floor now, when there is still time to change an architectural decision.

## Do this
1. Install OVR Metrics Tool on the device and enable its overlay.
2. With both hands tracked, one anchored object, and passthrough on, run for 10 minutes.
3. Record: average fps, 1% low, GPU level, and the time at which thermal throttling starts (if any).
4. Compare against the budget in `docs/02-tech/TECH-STACK.md` §4 and note the margin.
5. If below 72 fps, list the top three costs from the Unity profiler immediately.

## Done when
- [ ] A measured fps number on the weaker device, written down
- [ ] Thermal onset time recorded (or "none in 10 min")
- [ ] Margin against the 72 fps target stated

### Both traps are enforced in code, not prose

- **Editor/simulator:** the summary stamps `deviceModel`, `graphicsDeviceName` and
  `build: player / EDITOR — NOT ADMISSABLE`.
- **60 seconds called thermal-stable:** `requiredSeconds = 600`; a shorter run is written with verdict
  `INVALID` and "this file is evidence of a method, not a baseline".

### One conflict resolved, not ignored

The task says 10 minutes, the gate says **≥10**, and `PERFORMANCE.md` §2 says **15** (because
`RISKS.md` R10's trigger is "<72 fps at 10 minutes"). Resolution: **run 15, refuse to certify under
10** — satisfies all three and matches the method the submission quotes.

### The thermal number is not inferred from fps

An fps drop is the *consequence* of throttling. The event is `PowerManager.getCurrentThermalStatus()`
crossing ≥ 2, timestamped and kept as a full timeline. When the platform will not answer, the probe
reports **`unavailable`** rather than `0 = none` — a zero there would look exactly like a pass.
