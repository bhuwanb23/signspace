# P10.4 — Guard the freeze

**Phase:** P10 · **Est:** 5 min/week · **Depends on:** P9.8 · **Workstream:** W5
**Gate fed:** G10

## Why this exists
Three weeks is long enough for an idle 'quick fix' to break the submitted build. The freeze is a commitment.

## Do this
1. No commits to `main` until judging closes.
2. Any necessary fix goes to a branch and is only merged if the channel is actually broken.
3. Re-verify P10.1 weekly on the same day.

## Done when
- [ ] Branch untouched — **commits landed after the freeze** (paperwork; artifact unchanged)
- [ ] Weekly verification logged — 0 of 3 rows

## Artefacts produced
- `phases/p10-post/reverify-log.md` continued

## Traps
- Refactoring in the quiet weeks

## Outcome — 18 Nov 2026

The guard is `scripts/freeze_check.py`, designed to be re-run weekly and appended to `reverify-log.md`
without editing earlier rows. It is deliberately hostile to optimism: a missing tag is a FAIL, an empty
commit field is a FAIL, a version code that disagrees with the packaged manifest is a FAIL, and the three
account-side questions are NOT RUN rather than assumed.

**The guard's first acts were to fail the project and then to catch itself agreeing with a stale file.**
The record and `version-code.txt` both said 13 while the APK said 14; the tool now reads the APK, so that
class of drift cannot pass again. The APK itself was never rebuilt — hash and mtime unchanged.
